# How The Familia works

Mafia 1.2 is a 32-bit Windows program: `Game.exe` (game logic, missions, AI,
vehicles) plus the LS3D engine in `LS3DF.dll`, the archive reader `rw_data.dll`
and `IJoy.dll`. The Familia translates their x86 code ahead of time to C, compiles
it for AArch64, and answers the Windows and DirectX calls natively.

## Translation

`tools/translate.py` runs PCRecomp's disassembler and lifter over each module:

| Module | Treatment | Guest base |
|---|---|---|
| `Game.exe` 1.2 (unprotected) | lifted | 0x00400000 |
| `LS3DF.dll` 1.2 | lifted | 0x10000000 |
| `rw_data.dll`, `IJoy.dll` | lifted, rebased at build time using their relocations | 0x11000000, 0x11100000 |
| `ogg`/`vorbis`/`vorbisfile.dll` | native shim over the system's libvorbisfile | — |

- **Memory:** a 4 GiB guest address space reserved at a fixed host address.
  Guest pointers stay 32-bit, and objects handed to the game live inside it.
- **Calls:** direct calls go straight to the translated function. Indirect calls
  (vtables, callbacks) look the target up in a sorted address table, and an
  unknown target stops the program with its address.
- **x87:** the floating-point stack is computed in double precision, with float
  rounding at 32-bit stores and the control word's rounding honoured on conversion.
- **Threads:** the engine's streaming and sound threads run one at a time under a
  single lock, as PCRecomp's win32hle does.

## Platform layer (`runtime/`)

- **Windows:** PCRecomp's win32hle (`third_party/pcrecomp/win32hle`) provides
  kernel32, user32, the registry, files and case-insensitive paths. All writes go
  to `ports/the_familia/conf/`; the game data in `data/` is never modified.
- **Direct3D 8 → OpenGL ES 3.2** (`d3d8_*.c`): the fixed-function pipeline is
  emulated with generated shaders. GL entry points are loaded through SDL2, so
  the port uses whatever GPU driver the firmware's SDL2 uses.
- **DirectInput 8:** keyboard and mouse from SDL. On handhelds, PortMaster's
  gptokeyb turns the controller into keys and mouse movement (`familia.gptk`).
- **DirectSound 8:** a software mixer on SDL audio, with 3D positioning.
- **Videos** (`movie.c`): Game.exe's video player function is replaced. The AVI
  (Indeo 5 + MS ADPCM) and Bink files are decoded with a minimal FFmpeg build and
  drawn letterboxed as in the original.

## Performance layer

The H700's four Cortex-A53 cores are slow for a game written for desktop
Pentiums, so the hottest code paths are replaced or reorganised:

- **Native replacements** (`runtime/native_*.c`, hooked by `tools/native_hooks.py`
  from `config/native.json`). The translated function is kept as `<name>_orig`, and
  a wrapper calls the native C version. Covered: the engine's scene-graph update
  and culling, name lookups, lighting and occluders, vertex transforms and
  environment mapping, animation maths, skinned-mesh bounds, the software shadow
  rasterizer, CRT helpers, the archive decryption/decompression, and Game.exe's
  collision grid sweep.
  - Each group has a differential self-test against its translated original
    (`FAMILIA_NATIVE_CHECK=1`). A failing test turns off only that group.
  - The native code repeats the translated floating-point model exactly
    (`-ffp-contract=off`). Two exceptions run in single precision with NEON, as the
    game itself did on Windows (Direct3D sets the x87 to 24 bits): vertex lighting,
    within 1/255 per colour channel (`FAMILIA_LIGHT_EXACT=1` selects the exact
    path), and the cars' environment-map coordinates, within 0.001 of the texture
    (`FAMILIA_ENV_EXACT=1`).
- **Loop splicing** (`tools/splice_loops.py`, `config/splices.json`): the pixel
  conversion loops inside `ITexture::Create` are replaced in place, while the rest
  of the function stays translated.
- **GL thread** (`gl_thread.c`; stubs generated by `tools/gen_gl_thread.py`):
  GL calls are recorded and replayed on a second core, so the driver's work
  leaves the game thread.
- **Streaming ring** (`d3d8_stream.c`, off by default, `FAMILIA_STREAM=1` or the
  launcher's GPU streaming): dynamic and rewritten vertex/index data goes into a
  persistently mapped, fenced buffer. It is about 2 FPS faster, but the H700's Mali
  driver (libmali r20) keeps memory for every draw from such a buffer and never
  frees it (about 0.3 MB/s standing, far more driving). GL state, attribute and
  binding caches apply either way.
- **Shader cache:** the shader variants the game needs are recorded in
  `conf/shaders.bin` and built at startup, starting from the shipped
  `shaders.seed`.
- **Learned archive read-ahead** (`readahead.c`): the 64 KB blocks of the `.dta` archives the
  game reads are remembered per scene in `conf/readahead2.txt` (startup, and each scene behind a
  loading screen). A low-priority thread reads the startup list into the page cache at start
  and a scene's list when that scene loads, so a first drive through the city no longer waits
  on the SD card (FAT32, about 3 ms per small random read).
- **Memory** (1 GB handhelds): a texture's CPU copy (Direct3D's managed pool keeps one) is
  dropped once the texture is uploaded and settled, and read back from the GPU if the game
  ever locks it again (about 110 MB in the city at 32 bits). At each loading screen the guest
  heap returns the previous scene's freed memory to the system.
- **File lookups**: directory listings are cached, since LS3D looks for every texture as a
  loose file in each maps directory before reading the archive.
- **Profile-guided optimisation** of the whole binary (`tools/pgo.sh`).

The engine's function names and structure layouts come from our own reading of
the binaries, with the [mafia-re](https://github.com/Marvisak/mafia-re)
decompilation as a map. No code is taken from it.
